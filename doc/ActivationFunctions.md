# Fixed-Point Activation Functions

TAFFO supports fixed-point conversion of the following activation functions:

| Activation | Recognized names | Fixed-point implementation |
| --- | --- | --- |
| ReLU | `relu`, `reluf`, `relul` | Integer comparison and selection, or identity for unsigned values |
| Hyperbolic tangent | `tanh`, `tanhf`, `tanhl`, supported LLVM tanh intrinsics | 1024-element lookup table |
| Sigmoid | `sigmoid`, `sigmoidf`, `sigmoidl` | 1024-element lookup table |
| Swish | `swish`, `swishf`, `swishl` | 1024-element lookup table |

Functions generated by TAFFO's cloning process are recognized as well. For
example, `swish_clone0` is treated as `swish`. A clone suffix is accepted only
when it has the form `_clone` followed by one or more decimal digits.

Recognition is name-based. A user-defined function with one of the names above
is therefore assumed to implement the corresponding activation semantics.

## Example

The input to an activation must participate in TAFFO conversion and must have
valid range information. For example:

```c
#include <math.h>

float sigmoid(float x) { return 1.0f / (1.0f + expf(-x)); }

int main(void) {
  float __attribute__((annotate("target('main') scalar(range(-2, 1))"))) x = 0.5f;
  float __attribute__((annotate("scalar()"))) y = sigmoid(x);
  return y > 0.0f;
}
```

TAFFO treats the call to `sigmoid` as one supported mathematical operation. It
does not convert the operations in the function body individually. During
Conversion, the call is replaced with a lookup into a constant fixed-point
table.

## Compilation pipeline

Activation conversion uses the existing TAFFO pipeline:

```text
annotated floating-point program
              |
              v
Value Range Analysis (VRA)
computes the activation output range
              |
              v
Data Type Allocation (DTA)
selects input and output fixed-point types
              |
              v
Conversion
replaces the call with integer operations or a LUT lookup
```

The stages have separate responsibilities:

- VRA computes a mathematical interval. It can produce any interval `[min,
  max]`; it is not restricted to symmetric or power-of-two ranges.
- DTA chooses a representable fixed-point type whose domain contains that
  interval. The type records signedness, total bit width, and fractional bit
  count.
- Conversion consumes the types selected by DTA and emits the corresponding
  integer LLVM IR.

For a fixed-point value with raw integer representation `r` and `F`
fractional bits, the represented real value is

```text
x = r * 2^(-F).
```

The interval found by VRA and the full domain of the selected type need not be
identical. For example, VRA may infer `[-0.28, 0.74]`, while DTA selects a
signed type whose representable domain is approximately `[-1, 1)`.

## Value Range Analysis

The output ranges are computed as follows.

### ReLU

For an input interval `[a, b]`, ReLU produces

```text
[max(0, a), max(0, b)].
```

### Hyperbolic tangent and sigmoid

Both functions are monotonically increasing, so their output ranges are
obtained by evaluating the interval endpoints:

```text
tanh:    [tanh(a), tanh(b)]
sigmoid: [sigmoid(a), sigmoid(b)].
```

### Swish

Swish is defined as

```text
swish(x) = x * sigmoid(x).
```

Unlike the other LUT activations, Swish is not monotonic over its entire
domain. It has a finite minimum at approximately
`x = -1.2784645427610737`. VRA evaluates both endpoints and also evaluates this
critical point whenever it lies inside the input interval. This prevents the
output minimum from being underestimated.

## Lookup-table conversion

Tanh, sigmoid, and Swish share one LUT conversion implementation. A table is
generated at compile time for each distinct combination of:

- activation function;
- input fixed-point type;
- output fixed-point type;
- table size, currently fixed at 1024 elements.

The generated global name encodes these properties, allowing compatible calls
to reuse a table and preventing calls with different fixed-point types from
sharing an incompatible table.

### Generating the table

The table has 10 index bits because `2^10 = 1024`. Let:

- `B` be the total bit width of the fixed-point input;
- `F` be its fractional bit count;
- `L = 10` be the LUT index width.

The input must have at least 10 bits. Reducing it to the LUT width discards
`B - L` least-significant bits. Consequently, the reduced 10-bit fixed-point
representation has

```text
F_internal = F - (B - L)
```

fractional bits.

For every 10-bit pattern, table generation performs these steps:

1. Interpret the pattern as signed or unsigned according to the DTA-selected
   input type.
2. Convert its raw integer value `r` to the real input
   `x = r * 2^(-F_internal)`.
3. Evaluate the activation in `long double` precision.
4. Scale and quantize the result into the DTA-selected output type.
5. Store the resulting integer as a constant table element.

Sigmoid evaluation uses separate expressions for negative and non-negative
inputs to avoid unnecessary overflow. Table outputs are rounded toward
negative infinity and saturated to the representable output range.

### Runtime lookup

At runtime, no activation function is evaluated. Conversion emits:

```text
fixed-point input
       |
       v
right shift by B - 10
       |
       v
truncate to a 10-bit pattern
       |
       v
zero-extend to an unsigned index in [0, 1023]
       |
       v
address calculation and table load
```

A signed input uses an arithmetic right shift, while an unsigned input uses a
logical right shift. The resulting 10-bit pattern is always zero-extended when
used as an array index. Thus, for a signed input, the pattern `1111111111`
represents raw value `-1` during table generation but array index `1023` during
lookup. Both operations refer to the same table entry.

The LUT covers the full domain of the selected input type, coarsened to 1024
representative patterns. It is not normalized specifically to the VRA interval.
Entries corresponding to values outside the inferred interval are generated
but should not be reached when the range information is valid.

## ReLU conversion

ReLU does not require a table.

For a signed fixed-point type, Conversion emits the integer equivalent of

```c
result = input > 0 ? input : 0;
```

using a signed comparison and an LLVM `select` instruction.

For an unsigned fixed-point type, negative inputs are impossible and ReLU is
the identity function. Conversion emits an explicit integer identity operation
rather than returning the operand directly. This gives the result its own LLVM
value, to which TAFFO can attach the conversion metadata associated with the
original call.

## Limitations and requirements

- Activation recognition is based on the exact function names listed above,
  including valid TAFFO clone suffixes.
- LUT input types narrower than 10 bits are not supported.
- LUT output widths must be between 1 and 64 bits.
- The implementation uses the fixed-point types selected by DTA; it does not
  use an affine mapping tailored to the exact VRA interval.
- A 1024-entry table trades memory for a low-cost runtime index consisting
  primarily of a shift, truncation, address calculation, and load.

## Regression tests

End-to-end tests are available in:

```text
test/0_simple/relu
test/0_simple/sigmoid
test/0_simple/swish
test/0_simple/tanh
```

Each test compiles and runs both the original floating-point program and the
TAFFO-converted program, then compares their outputs. The ReLU test exercises
both potentially signed and non-negative inputs. The Swish test uses an input
range containing its non-monotonic critical point. The other tests cover a
standard math-library call (`tanhf`) and user-defined activation calls
(`sigmoid` and `swish`).

The tests can be run with:

```shell
cd test/0_simple
./run.py -only relu,sigmoid,swish,tanh
```
